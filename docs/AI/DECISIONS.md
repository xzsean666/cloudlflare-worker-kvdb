# DECISIONS.md — Key Architectural Decisions

This document records the foundational architecture decisions for `cloudflare-worker-kvdb`. Any modification to these decisions must be recorded here with explicit technical rationale.

---

## KD-1: Cloudflare Edge-Native Runtime (`workerd`) Without Node.js C++ Binaries

- **Decision**: The SDK is built exclusively using standard Web APIs (`fetch`, `crypto`, `Streams`, `TextEncoder`) and `@cloudflare/workers-types` bindings (`D1Database`, `KVNamespace`, `R2Bucket`, `DurableObjectStorage`).
- **Rationale**: Cloudflare Workers does not run in a standard Node.js VM; it runs on V8 `workerd`. Libraries with native C++ bindings (such as `better-sqlite3` or `pg-native`) cannot compile or execute in Cloudflare Workers.
- **Consequence**: The SDK is ultra-lightweight, has zero cold-start penalty, and deploys natively to Workers, Pages Functions, and Durable Objects.

---

## KD-2: Atomic Batch Aggregation via `db.batch()` as Default Write Pattern

- **Decision**: All multi-key operations (`setMany`, `deleteMany`, queue state transitions, and compound entity-index writes) must be bundled into atomic `db.batch([stmt1, stmt2, ...])` calls.
- **Rationale**: D1 writes route to a single global primary SQLite coordinator. Sequential unbatched writes cause repeated network hops and write-lock serialization (`SQLITE_BUSY`). Bundling statements reduces roundtrips by 85%-90% and ensures transactional atomicity.

---

## KD-3: Transparent 100-Bound-Parameter Safety Chunker

- **Decision**: The SDK enforces a transparent Parameter Chunker at the query/driver layer. No prepared statement generated by the SDK may exceed 100 bound parameters (`?`).
- **Rationale**: Cloudflare D1 throws a fatal exception (`D1_ERROR: too many SQL variables`) if any prepared statement contains > 100 bound variables. Batch inserts and `IN (...)` queries must be automatically split into safe statement chunks (e.g. 50-80 items per statement) and executed in a single atomic `db.batch()`.

---

## KD-4: Read-Your-Own-Writes (RYW) via D1 Sessions API and Bookmarks

- **Decision**: The SDK natively supports the Cloudflare D1 Sessions API (`env.DB.withSession(bookmark)`). The active bookmark is updated after writes and made available via `db.getSessionBookmark()`.
- **Rationale**: D1 read replicas distributed worldwide replicate asynchronously from the primary leader. Without bookmark coordination, reads immediately following a write could hit a slightly delayed replica and observe stale data. Passing bookmarks guarantees sequential consistency.

---

## KD-5: Monotonic Clock for Deterministic Ordering and Tie-Breaking

- **Decision**: The SDK embeds a monotonic clock generator (`getMonotonicNow()`) for all record timestamps (`created_at`, `updated_at`).
- **Rationale**: High-concurrency operations within a single isolate or rapid burst iterations can execute within the exact same millisecond, causing `Date.now()` to return identical values. A monotonic clock guarantees strictly increasing timestamps, preventing tie-break anomalies in cursor pagination and event sequencing.

---

## KD-6: Transparent R2 Blob Overflow Engine

- **Decision**: When a value's serialized size exceeds a configurable threshold (e.g. 64 KB or 1 MB), the SDK transparently offloads the binary payload to Cloudflare R2 and stores an encrypted metadata descriptor pointer in D1/KV. On read, the SDK transparently reconstitutes the payload from R2.
- **Rationale**: D1 has a hard row limit of 2MB, and large strings bloat SQLite B-tree pages, driving up row-read costs and memory consumption. R2 offers S3-compatible, zero-egress object storage ideal for large JSON documents or binary blobs.

---

## KD-7: Multi-Tier Caching Hierarchy (L1 Memory -> L2 Workers KV -> L3 D1)

- **Decision**: Data tables can be equipped with an optional multi-tier caching pipeline: L1 in-isolate memory LRU cache (<0.05ms) backed by L2 Workers KV (5-15ms edge read) backed by L3 D1 database.
- **Rationale**: Cloudflare D1 bills by rows read. Serving frequent reads from L1 memory or L2 Workers KV dramatically slashes D1 billing costs and brings edge read latency down to single-digit milliseconds.

---

## KD-8: Non-Blocking Background Workloads via `ctx.waitUntil()`

- **Decision**: The SDK accepts Cloudflare's `ExecutionContext` (`ctx`). Secondary tasks such as write-behind cache invalidation, cache warming, background GC, and metrics are dispatched via `ctx.waitUntil(promise)`.
- **Rationale**: `ctx.waitUntil()` keeps the isolate active in the background without blocking the HTTP response stream, ensuring that user-facing responses return in under 10ms.

---

## KD-9: Two-Tier Storage Interface Separation (`KVStore` vs `Driver`)

- **Decision**: Maintain a clear separation between:
  1. `KVStore`: Minimal key-value contract (`get`, `set`, `delete`, `has`, `clear`) used by cache stores and simple KV tables.
  2. `Driver`: Rich storage contract including JSON queries (`find`), dynamic schema, physical indexes, prefix scans, and transaction batching.
- **Rationale**: Prevents lowest-common-denominator trapping. Cache stores do not need to support complex SQL AST queries, and database drivers do not need to manage LRU eviction algorithms.

---

## KD-10: MongoDB-Style Query AST Lowered Directly to Native SQLite JSON

- **Decision**: Filter conditions (`where: { "profile.age": { $gt: 18 } }`) are parsed into a backend-neutral Query AST, then compiled into native SQLite functions (`json_extract(value, '$.profile.age') > ?` or `value->>'profile.age'`).
- **Rationale**: Allows database engine-level filtering directly in D1, avoiding the performance and cost disaster of fetching all rows into the Worker isolate to filter in JavaScript.

---

## KD-11: SingleFlight Request Coalescing in TieredCache

- **Decision**: `TieredCache.wrap()` incorporates a `SingleFlight` concurrency lock keyed by cache key.
- **Rationale**: When an item expires in high-traffic environments, multiple concurrent edge requests would otherwise miss the cache simultaneously, triggering the thundering herd problem and overwhelming upstream storage. SingleFlight coalesces all concurrent misses into a single fetch execution and broadcasts the result to all callers.

---

## KD-12: Parameter-Safe AST Lowering for High-Cardinality $in / $nin Expressions

- **Decision**: The SQL compiler automatically chunks `$in` and `$nin` expressions with > 80 values into `(col IN (...) OR col IN (...))` subclauses.
- **Rationale**: Abides strictly by Cloudflare D1's 100 bound parameters per query limit. Eliminates fatal `D1_ERROR: too many SQL variables` crashes without requiring manual query chunking by consumers.

---

## KD-13: Dead-Letter Queue (DLQ) Poison Pill Protection in JobQueue & QueueReaper

- **Decision**: `QueueReaper` inspects `attempts >= max_attempts` before resetting an abandoned active job. If maximum attempts are reached, the job is moved directly to `failed` state with `max attempts exceeded` metadata.
- **Rationale**: If a job repeatedly crashes a worker isolate (e.g. OOM or unhandled fatal trap), unconditionally resetting its state to `ready` causes an infinite loop ("poison pill"). Transitioning to `failed` preserves the poison job for auditing while protecting queue availability.

---

## KD-14: Zero-N+1 Batch Blob Lifecycle Management & Cascading Table Purging

- **Decision**: Table `deleteMany` and `clear` perform batched lookups (`WHERE pk IN (...)`) and chunked R2 `delete` calls (in groups of 1000) rather than firing individual single-key queries. Calling `table.clear()` cascades to purge the entire table blob directory in R2.
- **Rationale**: Eliminates the catastrophic N+1 query and N+1 R2 delete issue during mass deletion, saving up to 99% of Worker subrequests and preventing orphaned R2 storage costs.

---

## KD-15: Dual-Mode Method Decorator Architecture

- **Decision**: `@Cacheable` and `@CacheClear` support both modern TC39 Stage 3 decorators and legacy TypeScript `experimentalDecorators`.
- **Rationale**: Guarantees plug-and-play interoperability across all modern and legacy TypeScript frameworks (e.g. NestJS, Angular, Vite, esbuild, SWC) without requiring custom compiler flag configuration.
